> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the sign-in surface and the server-side security behind it, moving all three of the prototype's deliberately-insecure shortcuts server-side and discharging every authentication row in `SECURITY.md`.

## The three prototype holes — this phase's reason to exist

`SECURITY.md` names three things as deliberately insecure. Each is a task's acceptance criterion, not a nicety.

1. **The one-time code is generated and compared in the browser.** It must be generated server-side with a CSPRNG, stored only as a hash with a five-minute expiry, compared server-side in constant time, never sent to the client in any response, marked consumed on success, and bound to the session that started it.
2. **The OTP on/off flag lives in `localStorage`.** Anyone can set it to `0` and skip the second factor. `users.otpRequired` is the only source of truth, read server-side during the login handler. **The `localStorage` read and its `storage`/`focus` listeners are DELETED, not moved.**
3. **The three-attempt limit is cosmetic.** Six digits is a million combinations; without server enforcement it falls in minutes. Max three attempts per challenge server-side, then invalidate and force a resend.

## Task 2: The challenge lifecycle, as pure logic

**Files:**

- Create: `packages/domain/src/auth/otpChallenge.ts`, `otpChallenge.test.ts`

**Interfaces:**

- [ ] **Step 1: Write the failing test**

```ts
describe('challengeState', () => {
  it('is valid inside the five-minute window with attempts remaining', () => {
    expect(challengeState(aChallenge({ createdAt: 0, attempts: 0 }), 4 * 60_000)).toBe('valid')
  })

  it('expires exactly at five minutes, not after', () => {
    expect(challengeState(aChallenge({ createdAt: 0 }), EXPIRY_MS)).toBe('expired')
  })

  it('is exhausted at three attempts, so a fourth guess cannot be offered', () => {
    // Six digits is a million combinations. Without this the limit is cosmetic.
    expect(challengeState(aChallenge({ attempts: MAX_ATTEMPTS }), 0)).toBe('exhausted')
  })

  it('is consumed once used, so a code cannot be replayed', () => {
    expect(challengeState(aChallenge({ consumedAt: 1_000 }), 2_000)).toBe('consumed')
  })

  it('reports consumed before expired when both are true', () => {
    // Ordering matters for the message the reader sees; consumption is the
    // more specific fact.
    expect(challengeState(aChallenge({ consumedAt: 1_000, createdAt: 0 }), EXPIRY_MS + 1)).toBe('consumed')
  })
})

describe('canResend', () => {
  it('refuses inside the thirty-second cooldown', () => {
    expect(canResend(0, 29_000, 1)).toEqual({ ok: false, error: 'cooldown' })
  })

  it('allows exactly at thirty seconds', () => {
    expect(canResend(0, RESEND_COOLDOWN_MS, 1)).toEqual({ ok: true, value: undefined })
  })

  it('refuses past the hourly ceiling even when the cooldown has passed', () => {
    expect(canResend(0, 60_000, HOURLY_RESEND_CAP)).toEqual({ ok: false, error: 'hourly-cap' })
  })
})
```

- [ ] **Step 1: Write the three test helpers these tests consume**

`apps/web/lib/auth/testing/otpProbes.ts`:

```ts
/**
 * otpProbes — read-side helpers for the OTP service's integration tests.
 *
 * Factories and probes with no shared mutable state, per CLAUDE.md §2.3.
 * These read what the service persisted or printed; they never construct a
 * code, because a test that knows the code without reading it the way a
 * reader would is not testing the delivery path. Depends on the test Payload
 * instance and the console mailer's outbox.
 */
import { getTestPayload } from '../../testPayload.js'
import type { UserId } from '@travel-diary/domain/ids'

/** The most recent challenge row for a user, read straight from the database. */
export const latestChallenge = async (user: UserId): Promise<{ codeHash: string; attempts: number }> => {
  const payload = await getTestPayload()
  const found = await payload.find({
    collection: 'otpChallenges',
    where: { user: { equals: user } },
    sort: '-createdAt',
    limit: 1,
    depth: 0,
  })
  const row = found.docs[0]
  if (row === undefined) throw new Error('no challenge row for that user')
  return { codeHash: row.codeHash, attempts: row.attempts ?? 0 }
}

/**
 * The six-digit code as a reader would receive it — out of the mailer's
 * outbox, never out of the database, so the delivery path is exercised.
 */
export const readCodeFromOutbox = (mailer: { readonly sent: readonly { text: string }[] }): string => {
  const last = mailer.sent.at(-1)
  if (last === undefined) throw new Error('nothing was sent')
  const match = /\b(\d{6})\b/.exec(last.text)
  if (match?.[1] === undefined) throw new Error('no six-digit code in the message body')
  return match[1]
}
```

For `capturedLogLines`, use the console mailer's existing `logLines` accessor from Phase 0 — it already separates what was printed from what was sent, which is precisely the distinction this test needs. Do not build a second capture mechanism.

## Task 5: Anti-enumeration — identical response AND timing

**Files:**

- Create: `apps/web/lib/auth/signIn.ts` + integration test

`SECURITY.md`: "Return the same response and timing for 'no such account' and 'wrong password' — no user enumeration. The reset endpoint must respond identically whether or not the address exists."

- [ ] **Step 1: Write the failing test**

```ts
it('returns an identical response for an unknown address and a wrong password', async () => {
  const unknown = await signIn({ email: 'nobody@example.com', password: 'x' })
  const wrong = await signIn({ email: seeded.email, password: 'wrong' })

  expect(unknown).toEqual(wrong)
})

it('takes comparable time for an unknown address and a wrong password', async () => {
  // The response can be identical while the timing still says which branch
  // ran. A miss must hash a dummy password so both paths do the same work.
  const SAMPLES = 25

  const time = async (email: string): Promise<number> => {
    const started = performance.now()
    await signIn({ email, password: 'wrong-password' })
    return performance.now() - started
  }

  const unknown: number[] = []
  const wrong: number[] = []
  // Interleaved, so machine drift during the run cannot favour one arm.
  for (let i = 0; i < SAMPLES; i += 1) {
    unknown.push(await time('nobody@example.com'))
    wrong.push(await time(seeded.email))
  }

  const median = (xs: readonly number[]): number => {
    const sorted = [...xs].sort((a, b) => a - b)
    const mid = sorted[Math.floor(sorted.length / 2)]
    if (mid === undefined) throw new Error('no samples')
    return mid
  }

  const ratio = median(unknown) / median(wrong)
  expect(ratio).toBeGreaterThan(0.6)
  expect(ratio).toBeLessThan(1.6)
})
```

`seeded` is the fixture the surrounding integration suite already creates for a published user; name it however that file does rather than inventing a second one. The 0.6–1.6 band is deliberately wide: the assertion that matters is that one branch is not an order of magnitude faster than the other, which is what skipping the hash produces. A tight band would flake and get deleted.

The timing assertion must be robust enough not to flake. Take enough samples, compare medians rather than single runs, and if it still cannot be made reliable, say so and assert structurally that the miss path performs a dummy hash — with a comment explaining why the timing test was rejected.
